## 開発方針  
- **main ブランチは常に動作する状態を保つ**  
- **新機能は必ずブランチを切って開発する**  mainの状態になるように更新をするか、mainからブランチを伸ばす
- **PR（Pull Request）は必ず main に向けて作成する**  
- **PR のマージ順は開発の依存関係に従う（階段構造の PR は順番を守る）**  
- **レビューは全員で行うが、マージは@EikitiNが担当する**

---

## ブランチ戦略  
目的別にブランチを構成。…コンフリクトの軽減と細かなプルリクのため。`xxx`の部分には機能などがわかるような文言を書く。
どこに入れるかの判断基準は主な目的をどこに置くか。
例: cssに記述されたリンクをengine.jsで制御できるように変更する。→engineのブランチにする。主な目的はファイルのengine.jsによる集中管理であるから。
- `main`：安定版。マージは@EikitiNが行う。
- `feature/xxx`：新機能。現在実装が少しも行われていないもの。既存のものの改修ではない。例えばQR読み取りの初期実装など、複数ファイルにかかわるもの。
- `fix/xxx`：バグ修正  
- `ui/xxx`：UI改善  
- `command/xxx`：functions.js のコマンド追加  
- `engine/xxx`：engine.js の機能追加

---

## Pull Request のルール  
- PR は **必ず main に向ける**  
- PR の説明欄に以下を書く  
  - 目的  
  - 変更内容  
  - 関連 Issue  
  - マージ順の注意（必要な場合）  
- 階段構造のPRは順番を守る  
- 必要に応じて **Draft PR** を使い、誤マージを防ぐ  
- レビューは誰でも可能  
- マージは@EikitiNが行う
- 説明文に`Close #番号`を記載する。関連するIssueがマージ完了後自動でClosedになる

---

## Issue の使い方  
- 作業開始時(新規ブランチ設置時)に Issue を作成  
- Assignee は「その作業を担当する人」。Issueを作成した人は Assign yourself を押す
- 進捗は Issue に書き加える  
- 関連ブランチを Issue の「Development」からリンクする  
- バグ報告・改善案・質問も Issue に書く
- 積極的にメンションなどを利用し、詳しい人や担当者に確認を行う

## 開発の流れ
1. Issue を作成  
2. ブランチを画面右側のDevelopment Create branch for this issueから作成  
3. 作業する  
4. コミットする  
5. Issue に進捗を書く  
6. main に向けて PR を作成  
7. レビュー  
8. @EikitiNがマージ  
9. Issue を閉じる
